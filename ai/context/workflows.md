# FF-Hexas AI 工作流

开始任何流程前先执行 `AGENTS.md` 的批准要求和编辑边界。

## 1. 框架修复或功能

1. 定位公开 API、内部实现、调用点、配置、测试和审计条目。
2. 写明目标行为、非目标、兼容边界和验证范围，等待确认。
3. 对高风险区域先写失败反例或明确可观察的不变量。
4. 做最小且职责清晰的改动；需要时可以替换遗留实现，不围绕旧结构机械打补丁。
5. 运行受影响包测试；并发、生命周期或共享状态改动补 `-race`。
6. 更新公开契约、AI 入口和审计状态，说明未验证环境。

## 2. 遗留能力重新设计

1. 从审计证据还原当前行为和风险，不把它当成目标契约。
2. 明确选择：保留修复、整体重构、替换实现或删除能力。
3. 定义数据一致性、安全边界、失败模型、可观测性和资源所有权。
4. 检查 FF-Hexas 调用方、存量数据、配置和部署切换。
5. 设计迁移、验收、回滚和反例测试后再实施。
6. 完成后关闭、替换或拆分对应审计项。

## 3. goctl 或生成模板

1. 在 `tools/goctl` 独立 module 内读取命令、模板、fixture 和测试。
2. 明确生成输入、目标目录、覆盖行为和期望 diff。
3. 使用当前仓库的 goctl 源码，不安装 `@latest`。
4. 在临时目录验证生成结果，避免污染框架工作树。
5. 分别运行 goctl 测试与目标产物的构建或测试。
6. 注意现有 gogen 测试会删除已跟踪 `jwt.api` 的审计记录；验证后检查工作树。

## 4. 业务服务示例

只有用户明确要求创建示例、教程或验证应用时使用此流程：

1. 确认示例目的和目标 API/RPC 契约。
2. 按需读取 `ai/skills/zero-skills/upstream/references/` 中对应资料。
3. 先写 `.api` 或 `.proto`，确认后使用本地 goctl 生成。
4. 在示例目录实现逻辑、配置、测试和必要说明。
5. 通用参考与当前源码冲突时，以 FF-Hexas 实现和项目规则为准。

## 5. 审计或文档

1. 只记录可由代码、Git 元数据或实际命令确认的事实。
2. 区分当前行为、目标设计、已完成改动和待验证假设。
3. 更新入口路由，避免同一规则在多个文件漂移。
4. 至少执行文档空白、路径、链接和来源提交检查。
